## 修复 2: 错误返回加 `type` 字段 (P1 #9)

**V1.3.3 现状** (BEFORE):
```json
{"ok": false, "ask_message": "文件已存在: ...md (避免覆盖)"}
```
Agent 难以区分"软告警 (可问用户)" vs "硬错误 (应中止)"。

**V1.3.4 修复** (AFTER):
```json
{"ok": false, "type": "ask",    "ask_message": "文件已存在, 不覆盖: ...md。要 (1) 改描述/时间重命名  (2) 删除原文件  (3) 忽略这次记账  ?"}
{"ok": false, "type": "error",  "message":     "transfer 类型必须显式提供 --account (from) 和 --to-account (to)"}
{"ok": false, "type": "error",  "message":     "from 账户 '假账户' 不在 account-list.md (已注册: [...])"}
```

**Agent 行为约定** (V1.3.4+):
- `type="ask"` → Agent 用 `clarify` 工具问用户, 文件**保留**, 不覆盖
- `type="error"` → Agent **中止**这次记账, 告诉用户错在哪 (无需问)
- `ask_message` 字段只在 `type="ask"` 时存在
- `message` 字段只在 `type="error"` 时存在

**`type="ask"` 触发场景** (按用户偏好 soft alert):
- 同名文件已存在
- 解析不出账户 (走 resolver 5 层失败)

**`type="error"` 触发场景** (硬错误):
- 未知 `type` (非 expense/income/transfer)
- transfer 缺 `--account` 或 `--to-account`
- transfer from/to 账户不在 account-list.md
- `--account` (用户显式给) 不在 account-list.md (V1.3.4 新增)

## 修复 3: `--account` 用户显式无效账户 → type=error (V1.3.3 隐患)

**V1.3.3 隐患** (BEFORE):
- 用户给 `--account "假账户"` (拼写错), 不在 `account-list.md`
- `resolve_default_account()` 看 `user_provided_account not in account_names`, **跳过 user 走 note → config → learning → fallback**
- 静默用 fallback (Alipay) 写文件, 用户的"假账户" 意图被覆盖
- **污染 learning** (learning.json 记一笔 "Alipay 1 次", 但用户从未真的用 Alipay)
- **资产负债表错** (用户以为是 X 账户扣款, 实际是 Alipay)

**V1.3.4 修复**:
```python
# transaction_create.py create_transaction() 在 resolver 前先校验
if account and account not in account_names:
    return {"ok": False, "type": "error",
            "message": f"--account '{account}' 不在 account-list.md (已注册: {account_names})"}
```
不再 silent fallback, 不污染 learning。

**设计 rationale**: 用户显式给的账户是**最高优先级**信号。如果拼写错, 应该报错让用户知道, 而不是悄悄换成 fallback。**(V1.3.3 之前的 fallback 行为违反 "user > note > config > learning > fallback" 优先级, 因为 user 错的优先级应该 = 错误, 不是 = 跳过)**

## 坑 7 (V1.3.4 真实): Pyright 看不到 type narrowing, 需要 `assert`

**症状**:
- `create_transaction()` 在 transfer 分支明确赋值 `final_account = account` (非 None), `to_account_final = to_account` (非 None)
- 后面 for 循环用 `fm_account, fm_to_account = final_account, to_account_final`
- Pyright 报 `Argument of type "str | None" cannot be assigned to parameter "account" of type "str"`
- 因为 Pyright 在 for 循环里看不到 transfer 分支的 narrowing, 把 `final_account` 仍当 `Optional[str]`

**修复**:
```python
# BAD (Pyright 报错):
for i, rel_path in enumerate(rel_paths):
    if type_ == "transfer":
        if "/out/" in rel_path:
            fm_account, fm_to_account = final_account, to_account_final  # ❌ type error
            ...

# GOOD (显式 assert 帮 Pyright narrow):
for i, rel_path in enumerate(rel_paths):
    assert final_account is not None, "final_account 在此处必非 None"
    if type_ == "transfer":
        assert to_account_final is not None, "to_account_final 在 transfer 类型必非 None"
        if "/out/" in rel_path:
            fm_account, fm_to_account = final_account, to_account_final  # ✅ narrowed
            ...
```

**为什么用 `assert` 而不是 `cast()`**:
- `assert` 在 `-O` 模式会被移除, 运行时不影响 (transfer 路径下 `final_account` 确实非 None)
- `cast()` 是给 type checker 的 hint, 运行时不做检查 — 如果未来 transfer 分支有 bug, cast 不会捕获
- `assert` 是 self-documenting: "这里我**保证**非 None, 出错就崩, 强制我修"

**未来 session 跨分支赋值的 for 循环** 必加 `assert` 帮 Pyright narrow。
