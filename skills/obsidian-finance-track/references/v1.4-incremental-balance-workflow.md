# V1.4 增量余额刷新工作流 (类级 — 适用于未来所有 V1.x 增量 batch)

V1.4 给 finance track 加了**实时余额刷新**(写笔后立即刷新 `Accounts/balances.md`, 不再等 daily 18:00)。这次工作流暴露了**5 个类级模式**, 跟 V1.3.4 doc 的"坑 6/7/8 测试隔离"是同层抽象, 未来任何 V1.x 增量 batch 直接抄。

> 详细 ship 记录见 [`references/v1.4-fixes-and-pitfalls.md`](./v1.4-fixes-and-pitfalls.md) (修复 1 实时刷新 + 修复 2 transfer 字段 bug + Self-audit + commit 模板)。

## 模式 A: 改前备份 (仓库非 git 时)

**触发**: `~/.hermes/skills/<skill>/` 目录 `.git` 不存在 (本项目实情), 改代码前必须自备份。

**Recipe** (V1.4 真实用):
```python
import shutil, datetime, os
src = os.path.expanduser("~/.hermes/skills/productivity/obsidian-finance-track")
backup_root = os.path.expanduser("~/Obsidian/finance/.skill-backup")
os.makedirs(backup_root, exist_ok=True)
stamp = datetime.datetime.now().strftime("%Y%m%d-%H%M%S")
backup = f"{backup_root}/finance-track-{stamp}"
shutil.copytree(src, backup)
```

**为啥放 `~/Obsidian/finance/.skill-backup/` 而不是 skill 目录内**:
- skill 目录会被 `aweskill` / `cp` 同步覆盖, 备份会丢
- vault 目录 (`~/Obsidian/finance/`) 是用户私有数据 + 不会被 sync 动, **安全**藏备份
- 命名带 timestamp → 多次备份不冲突

**回滚 recipe** (出问题时):
```bash
rm -rf ~/.hermes/skills/productivity/obsidian-finance-track
cp -R ~/Obsidian/finance/.skill-backup/finance-track-20260604-132129 \
      ~/.hermes/skills/productivity/obsidian-finance-track
```

## 模式 B: stdlib unittest > pytest (零依赖项目)

**触发**: 项目 SKILL.md 写有 `tests/test_e2e.py`, 但实际目录**不存在** (V1.4 现场发现 finance skill 完全没 tests/ 目录)。PEP 668 阻止 `pip install pytest`, venv 装也超时。

**决策**: 走 stdlib unittest, 跟项目"零依赖"原则一致 (scripts/ 全部 stdlib)。

**Recipe** (V1.4 真实用, `scripts/tests/test_incremental_balance.py`):
```python
import os, sys, tempfile, shutil, unittest
SCRIPT_DIR = os.path.dirname(os.path.abspath(__file__))
SKILL_SCRIPTS = os.path.dirname(SCRIPT_DIR)
sys.path.insert(0, SKILL_SCRIPTS)  # 直接 import transaction_create, 不走 subprocess

# 隔离 vault factory
def _make_minimal_vault(tmpdir):
    os.makedirs(f"{tmpdir}/Accounts", exist_ok=True)
    for sub in ["Transactions/expenses", "Transactions/incomes",
                "Transactions/transfers/out", "Transactions/transfers/in"]:
        os.makedirs(f"{tmpdir}/{sub}", exist_ok=True)
    with open(f"{tmpdir}/Accounts/account-list.md", "w", encoding="utf-8") as f:
        f.write("| 账户 | 类型 | 币种 | 初始余额 |\n| Alipay | e-wallet | CNY | 1000.00 |\n")
    return tmpdir

class TestXxx(unittest.TestCase):
    def setUp(self):
        self.tmp = tempfile.mkdtemp(prefix="finance-test-")
        self.vault = _make_minimal_vault(self.tmp)
    def tearDown(self):
        shutil.rmtree(self.tmp, ignore_errors=True)
    def test_xxx(self):
        # 真实跑 create_transaction, 不 mock
        ...
```

**跑测试** (无 pytest):
```bash
cd ~/.hermes/skills/productivity/obsidian-finance-track/scripts
python3 -m unittest tests.test_incremental_balance -v
```

**为啥 stdlib unittest 够用** (V1.4 5 case 全过):
- 项目零依赖 → 装 pytest 是 OVERKILL
- unittest 支持 setUp/tearDown 隔离, 不需要 pytest fixture
- `python3 -m unittest` 自带 test discovery
- 缺点: 没有 pytest `-k` 关键字过滤, 没有 parametrize — V1.x 阶段 < 20 case 不痛

## 模式 C: E2E 测试作为"预存在 bug 探测器"

**V1.4 现场**: 写 5 个 e2e case, Case 1/3/4/5 通过, **Case 2 (transfer) fail**。深挖发现是 V1.3.4 一直存在的 transfer 余额 bug (compute_balances 假设的字段跟 build_frontmatter 实际产出不一致)。

**教训**: 写 e2e 时**故意覆盖最"危险"的数据流**, 暴露 V1.3.4 一直存在的隐患。不是写 happy path, 是写"如果这块坏了会爆" 的 case。

**V1.4 5 case 按"暴露 bug 概率"排序**:
| Case | 暴露的潜在问题 |
|------|----------------|
| 1. expense 增量 | 受影响账户逻辑是否对 |
| 2. transfer 增量 | **V1.3.4 transfer 字段 bug** ← 实际命中 |
| 3. 无旧 snapshot fallback | 边界条件 |
| 4. daily source 字段 | 兼容性 / 字段不污染 |
| 5. incremental == full | **核心正确性保证** — 最该写的 case |

**未来 V1.x 增量必加**:
- "写 X 笔后, incremental == compute_balances" 通用 case (任何改了余额计算的 PR 都要加)
- "transfer 类型必须有 case" (build vs read 字段最易脱节, V1.3.4 坑 6 教学)

## 模式 D: 真 vault 测试 + 强制清理

**为啥有时要测真 vault 而不仅是隔离 vault**:
- 隔离 vault 跑通 ≠ 真 vault 跑通 (vault 有 `.obsidian-finance/learning.json` 等隐藏状态, 隔离 vault 复制不到)
- 真实数据能暴露"config `parse_config_yaml` fallback 路径错" 这类**部署态**问题

**V1.4 真 vault 测试 recipe**:
```python
import subprocess, glob

# 1. 记录写笔前状态
bal_path = f"{vault}/Accounts/balances.md"
mtime_before = subprocess.check_output(['stat', '-f', '%Sm', bal_path]).decode().strip()
existing = read_existing_balances(vault)

# 2. 写笔 (这里会污染 vault)
r = create_transaction(vault_root=vault, type_='expense', amount=50, ...)

# 3. 验证 mtime 变 + 余额对
mtime_after = subprocess.check_output(['stat', '-f', '%Sm', bal_path]).decode().strip()
assert mtime_after != mtime_before
assert read_existing_balances(vault)[("Alipay", "CNY")] == expected

# 4. **强制清理** (必做, 否则 vault 永久污染)
# 4a. 删除测试文件
for f in glob.glob(f"{vault}/Transactions/expenses/2026-06-04-*e2e*"):
    os.remove(f)
# 4b. 用 refresh_balance_snapshot_incremental 恢复 (不是简单 os.remove balances.md,
#     因为 daily 18:00 还会再生成, 必须重算 + 写回)
refresh_balance_snapshot_incremental(vault, affected_accounts={"Alipay"})
assert read_existing_balances(vault)[("Alipay", "CNY")] == 0.00
```

**V1.4 现场坑**: 删掉测试 expense 文件后, balances.md 还显示 -50 (因为还**没重算**, 旧快照值还在)。**必须再调一次 refresh_balance_snapshot_incremental** 才会用 compute_balances 实时重读 Transactions/。

**未来真 vault 测试纪律**:
- 优先用隔离 vault + `shutil.copy(vault/default_accounts.yaml, ...)` 模拟真实数据
- 必须用真 vault 时, **先问 Evan 同意** + 提前记录"mtime 前/后 + 余额预期" + 强制 4 步清理
- 清理完跑一次 `assert 余额 == baseline` 才算清理成功 (不能 os.remove 后就走)

## 模式 E: "语义价值 > 性能" (Evan 决策原则)

**V1.4 Evan 选 B (增量) 不选 A (全量)**, 理由: **语义/审计价值 > 性能数字**。

| 选项 | 性能 | 语义/审计价值 |
|------|------|----------------|
| A 全量写 | O(N) 一次 | mtime 变, 但不知道谁触发的 |
| **B 增量** | **O(N) 一次 (但只对 1-2 账户重算) + 受影响账户用新值** | **mtime 变 + source 字段 = 审计清晰 + affected_accounts 显式** |
| C 半增量 | O(N) 一次 | 半清晰, 用户查"刚记的那笔"看到, "整体余额"还是昨天的 |

**Evan 原话**: "增量好, 因为记账后, 只需要更新受影响的账号, 其他没动的不用刷新。"

**未来给 Evan 提案时**:
- 强调**语义/审计价值** (mtime 变 = 用户感知"实时"; source 字段 = 审计清晰; affected_accounts 显式 = 不是静默全量)
- 不要只卖性能数字 (B 实际不是严格 O(1), compute_balances 还是要扫全 Transactions)
- 让 Evan 知道"你选了语义价值, 不是选了性能", 避免后面解释"为啥增量没省多少时间"
